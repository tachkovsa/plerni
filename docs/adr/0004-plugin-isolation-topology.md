## Context

Equal citizenship means the same contracts and the same admission pipeline. It does not mean the same trust. D11's choice is topology instead of trust: an operator-approved plugin, including every first-party plugin, runs where the platform puts it, and it reaches tenant data and the network only through that placement.

Three different failures get called "isolation" and need different mechanisms.

1. **Fault.** A plugin crashes, leaks, blocks, or emits a malformed frame. The kernel and the other plugins have to keep serving.
2. **Confusion.** A plugin uses the wrong tenant, presents the wrong identity, or opens a connection it was not granted. Tenant data and egress have to stay on the broker's terms.
3. **Hostility.** The installed code attacks the runner: another plugin's memory, the supervisor's files, the helper cache, or the kernel interface. That is a sandbox problem.

The operator-approved tier exists for the first two. The third is the untrusted tier, which the spec defers. Calling a runtime that only handles the first two a sandbox is the failure named in spec §17 risk 2.

Spec §2 is the shape that stdio and an egress-denied network can share. A plugin cannot be both a kernel child, because stdio needs a parent, and a resident of an egress-denied container, because a container boundary needs sockets. The plugin-runner hosts the supervisor. The supervisor keeps one mutually authenticated channel to the kernel on the internal-only network, spawns each plugin child, and speaks framed NDJSON over that child's stdio. The capability credential is issued at spawn and binds every call to plugin identity, version, and grants.

v1 runs one isolation mode: one process per plugin (spec §16). The process is never per tenant. Pooled plugin processes are rejected because pooling collapses per-plugin identity (spec §18). `worker_threads` as a boundary, Wasm plugins, and a gRPC sidecar as the default are already rejected (spec §18). `node:vm` is rejected below with that in-process shape: the module is not named in §18, and it is not a security mechanism. This record scores the three live shapes against the spec and the spike, and it records which shape v1 ships.

## Options

### 1. In-process isolates

`worker_threads` run JavaScript on another thread of the same OS process. Each worker has its own V8 isolate and its own heap. Ordinary messages are cloned. A buffer is shared only when the caller transfers an `ArrayBuffer` or uses a `SharedArrayBuffer` ([worker_threads](https://nodejs.org/docs/latest-v24.x/api/worker_threads.html), v24.22.1, the major pinned in `.nvmrc`). An object retained in one worker stays in that heap. It does not expose another plugin's in-flight calls.

The rejection stands on the risks that remain. The worker and the supervisor are one process, so a native crash or an out-of-memory fault takes the runner down, and there is no per-plugin pid to restart. Most Node.js APIs are available inside the worker. Those APIs run with the process's privileges: the environment, the filesystem, and the network the process can use. Node documents workers for CPU-intensive JavaScript, and documents that they do not help much with I/O-intensive work. A port call is I/O-shaped. A `SharedArrayBuffer` used on purpose would also sit outside the copied-byte accounting ADR-0006 requires.

The same process shape is the default for a Backstage backend: plugins are installed in one backend process, and splitting them into several processes is an optional deployment choice ([Backend Plugins](https://backstage.io/docs/backend-system/architecture/plugins/)). Logical rules ("plugins do not call each other in process") are conventions inside one process. They do not survive a plugin that ignores them.

Node's permission model does not repair this. On v24.22.1 it is a seat belt for trusted code: it "does not protect against malicious code", and "malicious code can bypass the permission model" ([permissions](https://nodejs.org/docs/latest-v24.x/api/permissions.html)). A default `Worker` with no `execArgv` keeps the parent's command-line flags, including `--permission`. An explicit `execArgv` replaces those flags, and the worker keeps the grants only when the flags are listed again. Spec §18 already rejects `worker_threads` as a boundary because Node capabilities leak across it.

`node:vm` is the same in-process shape, one step weaker. The module states that it is not a security mechanism and must not run untrusted code ([vm](https://nodejs.org/docs/latest-v24.x/api/vm.html)). A `vm` context is a global object inside an isolate. The V8 embedder guide defines an isolate as a VM instance with its own heap, and a context as an execution environment inside one instance of V8 ([embed](https://v8.dev/docs/embed)). The same guide says the first context is the expensive one and later contexts are cheaper. That is startup cost. It is not the B1 sustained rate, and it is not a security boundary. Embedding a second isolate beside Node keeps the plugin inside the supervisor's process and adds a runtime the mainstream-only invariant (spec §1 invariant 5) does not call for. The Wasm rejection in spec §18 is the same class of objection.

### 2. One supervised OS process per plugin, brokered, with egress denied by placement

The runner supervisor spawns one Node child per installed plugin and talks framed NDJSON over that child's stdio. The supervisor bridges every child to the kernel on one mutually authenticated channel per runner: mTLS with operator-issued certs (spec §4.4). Identity on that channel is the credential the supervisor stamped at spawn. A field the child writes is an untrusted hint. Tenant, actor, grants, and deadline are host-constructed on every port call. The plugin holds no database connection and submits writes as WorkUnits the broker commits. A cancel the plugin ignores still cannot commit: the broker checks the fencing token at commit time. The child shares the runner's network namespace. Direct outbound networking is a property of that placement: in production the runner can reach the kernel broker and any internal service on that plugin's operator allowlist, and nothing else. External HTTP, telemetry, and subprocess egress go through tenant-bound broker ports.

This is the same class of boundary VS Code and Grafana use for stability, and no more. VS Code runs extensions in an extension-host process so a misbehaving extension does not take the workbench, and documents that the host "has the same permissions as VS Code itself" ([extension runtime security](https://code.visualstudio.com/docs/configure/extensions/extension-runtime-security)). Grafana launches each backend plugin as a subprocess over gRPC so a plugin panic is not a server panic, and so the plugin is outside the server's address space ([plugin backend system](https://grafana.com/developers/plugin-tools/key-concepts/backend-plugins/)). Neither description is a claim that the subprocess is a hostile-code sandbox.

Node's threat model matches that limit. Node trusts the code it is asked to run, including JavaScript, WASM, and native code, and that code inherits the privileges of the execution user ([SECURITY.md](https://github.com/nodejs/node/blob/main/SECURITY.md)). The v24.22.1 permission document says a process under `--permission` can still call `process._debugProcess(pid)` and force another Node process of the same OS user to open its inspector, and that stopping this is the operator's job: a different OS user, or an OS isolation mechanism outside Node. Same-UID file writes, cache tampering, and dumpable memory sit in that same class.

### 3. An OS sandbox per plugin, or no local code at all

The spec's untrusted tier is "OS/container isolation OR remote-integration-only". Both are real, and both are deferred.

An OS sandbox gives the plugin its own user, mount, and pid namespace, and a cgroup, inside a container runtime. A stricter runtime intercepts the system-call surface instead of letting the process call the host kernel. gVisor states that goal directly: it exists to reduce exposure of kernel bugs to untrusted userspace, by having the Sentry implement the system API and by minimizing the host calls the Sentry itself can make ([security model](https://gvisor.dev/docs/architecture_guide/security/)). gVisor also states the performance shape: interception cost falls on system-call-bound work, and the platform choice matters (KVM on bare metal, `systrap` inside a VM, because nested virtualization is the expensive case) ([performance](https://gvisor.dev/docs/architecture_guide/performance/), [platforms](https://gvisor.dev/docs/architecture_guide/platforms/)). A plain container shares the host kernel; gVisor is one way to shrink that share. This record does not choose the runtime.

Remote-integration-only never runs the plugin on the runner. The operator calls scoped APIs and receives webhooks. That contains hostile code by keeping it off the host. It cannot host a first-party plugin that submits WorkUnits, holds subscription cursors, and serves the declarative UI, unless that plugin is rewritten as an external service. Trust tiers may change isolation. They do not change the contract. Remote-only is a placement for code the operator does not want on the runner, not a second contract for first-party domains.

## Decision

1. **v1 has one isolation mode: one supervised Node child process per installed plugin.** The supervisor spawns it, stamps its capability credential, and is the only thing that multiplexes it toward the kernel. First-party and third-party operator-approved plugins use this mode. The contract does not change with the tier. `worker_threads` and `node:vm` are rejected with the in-process shape. A worker is rejected because it shares the supervisor's process, because Node APIs are available there, and because a crash takes the runner down. Separate V8 heaps do not change that.
2. **The process is not a tenant.** Every tenant of that plugin shares the process. Tenant, actor, plugin identity, version, grants, trace, and deadline are constructed by the host. The plugin does not mint them, does not hold a database connection, and does not commit except through a fenced WorkUnit. RLS and the application-layer tenant guard stay the tenancy floor (spec §5). A per-tenant process is rejected. A pool that co-locates plugins in one process is rejected because pooling collapses per-plugin identity (spec §18).
3. **Production egress is placement.** The runner's network can reach the kernel broker and the operator's explicit per-plugin internal allowlist. Other egress is a broker port with tenant context. A single-host development composition may relax that placement, and any such composition says so in the operator-facing description. The relaxation is not a second, silent production mode.
4. **The operator-approved tier is a trusted-code runtime.** It contains a faulting plugin (crash, malformed frames, a sibling left serving) and a confused plugin (forged identity on the mux, a cancel that must not commit, a tenant it cannot select). It does not contain a hostile plugin that shares the runner's user. Plugin-to-plugin tampering, plugin-to-cache tampering, dumpable memory after `exec` or re-exec, and same-user file writes are accepted residuals of this tier. They are the reason the tier is named operator-approved. The basic seccomp filter and the sealed helper in the #51 harness stay what ADR-0006 says they are: a backstop for the memory ceiling. Node's `--permission` flag is not adopted as the boundary.
5. **The untrusted tier is not built.** OS/container isolation and remote-integration-only stay the two deferred shapes in spec §4.4. This record does not pick a container runtime, a microVM, or a webhook profile. UI follows the same honesty: plugin screens stay declarative until P5, so the browser is not a second plugin runtime (D12).

## Consequences

- P2's runner implements decision 1–4. The conformance suite keeps the B4, B5, and B6 hostile cases, including the stamping vacuity control, because a suite that only runs with stamping on cannot see the identity boundary fail.
- Acceptance test §16.12 (direct network from a plugin with no grant fails) is a topology test. It passes only on a runner whose network placement is the production one. A development composition that relaxes placement does not count as that test.
- Acceptance test §16.13 (tenant GUC, extra policy, smuggled `set_config`) stays the tenancy battery. Passing it is required even though the process boundary exists. The process is not the tenant boundary.
- Crash recovery "kernel + siblings serving within 10s" (spec §16.4, P2 exit) is a P2 target. B5 shows the sibling and the fencing token survive a crash. It does not measure the 10 seconds.
- Flow control, frame caps, and the seccomp ceiling backstop remain ADR-0006. This record does not adopt the failed B3 numbers (partial high-water 69632; accounted totals 106496, 57344, 155648; receive buffer 131072) and does not publish a replacement buffer budget.
- A distinct uid and a user namespace are how the untrusted tier separates a plugin from the runner user. They are not requirements of the operator-approved process. A cgroup pid limit is an availability knob a later runner may set; this record does not require one, and setting one does not turn the tier into a sandbox.
- Wasm plugins and a gRPC sidecar as the default transport stay rejected (spec §18). The IPC transport remains framed NDJSON over stdio, bridged on one runner channel, as spec §4.4 names it.

## Flip conditions

- **Register flip (D11).** Demand for untrusted third-party code builds the container tier at P5. Spec §15 starts that phase only on measured demand: at least three external authors with real installs through manual distribution. Remote-integration-only may be chosen then, for plugins that should not run on the runner, under the same trigger. Until then, v1 stays one process per plugin. A same-UID attack is not this flip. It is the residual decision 4 accepts.
- **This record is withdrawn if the topology evidence flips.** A promoted harness in which a child crash takes down a sibling or the supervisor (B5), or in which a child-supplied identity is accepted on the mux (B6), falsifies the process boundary. The track returns to the maintainer. Tightening the seccomp filter is not a repair for that result.
- **A B1 miss after the flow-control redesign is ADR-0006's flip.** The frozen shape missing ≥ 5000 round-trips/s or p99 ≤ 10 ms is a reason to revisit the buffer terms in that record. It is not a reason to move plugins into the runner process, into a worker thread, or into an in-process isolate, and it is not a reason to start the container tier.
- **B3 stays a flow-control fact.** The FAIL in the spike report opened ADR-0006. It does not reopen the choice of process topology.
