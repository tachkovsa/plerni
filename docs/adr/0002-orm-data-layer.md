## Context

The kernel stays small and free of domain nouns. Every feature, including every first-party feature, is a plugin. Plugins depend on each other through public contracts and the event log ([ADR-0003](0003-outbox-pgboss.md)), and they never read each other's tables (spec §4.8). A plugin owns its tables and its SQL migrations. Installing one must not require a kernel schema edit, a kernel type edit, or a kernel release.

D06 chooses the typed query API for the kernel. The register records that β and γ independently selected Kysely over node-postgres, with Drizzle as the ergonomics fallback and Prisma 6 rejected for this project on generated-type compile cost. The register leaves that choice gated on Spike A. This record applies the gate to the versions current on 2026-10-25 and states how the chosen API meets four criteria the spec already binds:

1. **Plugin-owned schemas.** A plugin adds tables by shipping SQL. The kernel source does not change.
2. **Migration order across dependent plugins.** Replicas apply one order. The order follows required ports in the manifest. It does not authorize a cross-plugin foreign key.
3. **Tenant isolation.** Transaction-local tenant context on a PgBouncer transaction-mode pool, fail-closed when the context is missing, and recovered when a session is contaminated.
4. **Testability.** The tenancy path and the typecheck path have a rerunnable oracle against PostgreSQL. A stand-in for the query API is not evidence of RLS.

Plugins never hold a database connection (ADR-0001). The query API belongs to the kernel and the broker. Plugin SQL is declared, admitted, and executed inside the broker's transaction (spec §4.3).

In the published `kysely@0.29.6` build, `TransactionBuilder.execute` calls `provideConnection`, then `beginTransaction`, the callback, and `commitTransaction` or `rollbackTransaction` on that same connection. `PostgresDriver.beginTransaction` sends the text `begin` when isolation level and access mode are unset, and `commit` / `rollback` the same way, each as a parameterless query. In `pg` 8.23.1, `Query.requiresPreparation` prepares when the query mode is extended, a name is set, a row limit is set, or the values list is non-empty. A parameterless text with no name is not prepared, so those transaction commands stay simple queries. That is the split the report records, and it is how PgBouncer sees the transaction end. A statement name is present only when the caller set one. With no name, A4 observed an empty name. That is the unnamed discipline.

The current PgBouncer manual (retrieved 2026-10-25) still says: transaction mode releases the server connection when the transaction finishes; `max_prepared_statements` defaults to 200 and tracks protocol-level named prepared statements; `0` disables that support in transaction and statement mode; `PREPARE`, `EXECUTE`, and `DEALLOCATE` are forwarded to PostgreSQL, with `DEALLOCATE ALL` and `DISCARD ALL` as the exceptions that clear tracked statements; `server_reset_query` defaults to `DISCARD ALL` and does not run in transaction mode unless `server_reset_query_always` is on (default 0). The measured binary is 1.26.0, as in the report and ADR-0007. Plan §3.1 A4 already records that this setting caches named client statements and cannot help mandated unnamed traffic.

Spike A did not measure Drizzle, Prisma, a Prisma driver adapter, PostgreSQL 16 or 17, or PgBouncer 1.26.1.

## Decision

1. **The kernel query API is Kysely 0.29.6 on node-postgres `pg` 8.23.1.** One `Kysely` instance per pool, `PostgresDialect` constructed with a `pg.Pool` the kernel owns ([Getting started](https://kysely.dev/docs/getting-started)). The pool is visible at the construction site. The acceptance compiler for this API is TypeScript 5.9.3 with `strict`, which is what A5 ran. Kernel code does not call `pool.query` for any statement that belongs to a tenant transaction.
2. **Tenant work runs inside `transaction().execute` with no isolation or access-mode override.** The published 0.29.6 driver then sends `begin`, the callback, and `commit` or `rollback` on the one connection `provideConnection` acquired. The ordered hygiene protocol (plan §2) runs at the start of that callback, before tenant access. `BEGIN` has already been sent. Inspect, before any local override: each named `plerni.*` setting via `current_setting(name, true)`, treating `''` as absent; `current_user = session_user`; `search_path` equal to its pinned value. On contamination, terminate the executing backend and discard every still-open client socket on that pool ([ADR-0007](0007-pooled-contamination-recovery.md)), then retry at most twice and fail loud. On a clean session, `set_config(name, value, true)` (PostgreSQL 18: `is_local` true applies for the current transaction only, [`set_config`](https://www.postgresql.org/docs/18/functions-admin.html)) and read the authorized value back. Only then touch tenant tables. The callback's transaction object is the only executor. A query on the outer `Kysely` instance is a different checkout.
3. **The default client leaves statement names empty.** Named statements stay the A4b branch: installed for that experiment, `max_prepared_statements` above 0, removed afterward. A4 measured unnamed traffic as more expensive than named on the direct connection (means 30.4%, 27.3%, and 25.7%). That cost is accepted. Adopting names as the default is a later record. A4b shows the branch can pass. SQL `PREPARE` / `EXECUTE` / `DEALLOCATE` are not the naming mechanism.
4. **SQL is the schema source of truth. The ORM migrator is not the journal.** Kernel and plugin migrations are ordered SQL files. The kernel journal applies them. Kysely's `Migrator`, `drizzle-kit`, and Prisma Migrate do not. `kysely-codegen` 0.20.0 runs in CI against the migrated kernel schema, its type-only output is committed, and a diff fails the check. The spike proved that check with two drift fixtures. The check becomes a required workflow when the kernel schema lands. Codegen is not in the appliance boot path.
5. **The kernel `Database` interface names kernel tables only.** Plugin schemas are excluded (`--default-schema` and `--include-pattern` / `--exclude-pattern` scoped to the kernel schema). Adding or upgrading a plugin does not change a kernel source file. The broker executes a plugin's admitted SQL text with bound parameters inside the kernel transaction. Plugins do not depend on Kysely and do not receive a `Pool`, in production or in tests.
6. **Each plugin owns one PostgreSQL schema, under D08.** The schema holds tables, indexes, and constraints. It does not hold functions, triggers, or `DO` blocks. The migration role has `CREATE` on that schema only, no `CREATE EXTENSION`, and no `SECURITY DEFINER`. The kernel bootstrap provisions the extension allowlist (`vector`, `pg_trgm`). The only cross-schema references are the declared read-only `REFERENCES` grants on the kernel identity columns `users(id, tenant_id)`. Every migration carries the signed approval artifact spec §4.6 already requires.
7. **Tenant-domain tables, kernel and plugin, share one shape.** `tenant_id` is `NOT NULL`. Row security is enabled and forced, so the table owner is also subject to it ([row security](https://www.postgresql.org/docs/18/ddl-rowsecurity.html)). Superusers and `BYPASSRLS` still bypass; the app role in the spike is `NOBYPASSRLS` (plan §2). Exactly one canonical permissive policy exists, and the boundary checker compares its text, because PostgreSQL OR-combines permissive policies. The checker also requires ownership inside the plugin schema, tenant-preserving composite foreign keys `(tenant_id, id)`, and runtime-DML-only grants. `GRANT ALL` stays forbidden. Kernel-internal machinery tables (outbox, delivery records, the job store, the AI budget ledger, relay state) stay a separate class: no tenant RLS, access only through the named service identities in spec §5. Per-tenant reference rows ship as versioned per-tenant migrations, applied in background batches, off the request path. They are not part of the schema order below.
8. **The journal orders migrations by the manifest, then by filename.** Pending kernel SQL runs first, so a plugin can declare the spec's read-only `REFERENCES`. Plugin packages then run in topological order of "requires a port this plugin provides" (spec §4.2). Ties break by plugin id, bytewise ascending, so every replica computes one order. A cycle fails admission for every plugin on the cycle and for every installed plugin whose required-port chain reaches that cycle. Nothing in that set migrates. Inside a package, filenames sort alphanumerically, the ordering rule Kysely documents for its migrator. Event subscriptions are manifest declarations. They are not migration edges: a subscriber does not need the publisher's tables, and spec §4.8 keeps cross-plugin reads on the owner's port or on the event log. A statement that names another plugin's schema fails the boundary checker.
9. **Pooled sessions stay clean by the hygiene protocol and by ADR-0007.** The pooler is PgBouncer in transaction mode. `server_reset_query_always` stays 0. `ignore_startup_parameters` stays empty. PgBouncer 1.26.0 tracks `search_path` by default on PostgreSQL 18 ([changelog](https://www.pgbouncer.org/changelog.html), 2026-09-23). The 1.26.1 notes (2026-10-14) leave further `search_path` tracking bugs for a later release, and they say listing `search_path` in `ignore_startup_parameters` restores the 1.25 ignore behavior. This record does not turn that ignore on. Missing context fails closed twice: the policy returns no rows, and the application guard raises. Session `SET`, `LISTEN`, and session advisory locks stay off pooled connections (spec §5). Activation and migration take their advisory lock on an unpooled connection (spec §7).
10. **Tests hit PostgreSQL.** The spec §5 two-tenant suite — CRUD, joins, foreign keys, jobs, events and subscriptions and cursors, missing context, pool reuse, rollback, search, export, and tenant-GUC manipulation — runs against a real migrated database through the `NOBYPASSRLS` app role, with the vacuity control the spike already ran. The spike suite, including the raw-`pg` control on both datasources, is the regression for pinning, leak-freedom, and contamination recovery. The journal has its own fixture: a dependent declared ahead of its provider is refused, and a foreign key into another plugin schema fails the boundary checker. The A5 acceptance point remains band 75, 375 queries, at most 120000 ms and 3906250 KiB on the CI runner class, TypeScript 5.9.3, `strict`, corpus lint intact. A unit test that replaces the query API with an in-memory fake does not count for any of those. A result that would flip this record follows plan §3.0, including at least three runs with the environment recorded. An environmental failure is an invalid run and produces no verdict.

WorkUnit (D07) is how a plugin writes. The broker runs the plugin's admitted statements, the audit row, and the outbox row in one `transaction().execute` callback. IPC waits stay outside that callback (spec §4.3). This record does not reopen D07 or D10.

## Consequences

- Adding a plugin table is a SQL file in that plugin, a boundary-checker run, and a journal entry. It is not a kernel type change and not a kernel release by itself. The codegen include list for the kernel interface is part of the purity boundary. A plugin schema that appears in that interface fails review.
- `kysely` 0.29.7 is current upstream and is not what A1–A5 ran. Its release notes (2026-10-17) describe connection-release fixes on controlled transactions (`startTransaction`) and releasing a PostgreSQL client destroyed while a connection is still being acquired. This decision uses `transaction().execute`. Those notes are not evidence that the callback path is unchanged. The pin moves only with an A1–A3 rerun.
- The kernel runtime dependencies this decision adds are `kysely` 0.29.6 (MIT, no dependencies of its own) and `pg` 8.23.1 (MIT), with the driver dependencies named above. `kysely-codegen` stays a development dependency.
- The scored pooler is 1.26.0 on PostgreSQL 18.6. Current PgBouncer docs still default `max_prepared_statements` to 200 and still skip `server_reset_query` in transaction mode. PostgreSQL 16 and 17 were not scored. The spec floor remains 16, and a deployment below 18 is unmeasured pooler behavior for the `search_path` tracking 1.26.0 added.
- Unnamed extended queries are re-prepared on every execution. The three A4 means are the price of that, measured on a direct connection. The pooler does not cache them while `max_prepared_statements` is 0.
- The drift gate has fixtures and is not yet a required check, because the kernel schema is not in the tree. Once that schema lands, a stale interface fails the build.
- Read replicas remain incompatible with transaction-pinned `set_config`, as spec §5 already says.
- Kysely's `Migrator`, Drizzle Kit, and Prisma Migrate are not a second migration history.

## Rejected alternatives

- **Drizzle ORM 0.45.4 as the kernel client.** It can speak node-postgres (`drizzle-orm/node-postgres` on a `pg` `Pool`) and it can generate SQL. The register keeps it as the fallback if typecheck ergonomics fail at the A5 acceptance point. Spike A did not fail that way, and Drizzle was not measured. Its typed surface is a runtime schema module, so plugin tables described there become application imports. Database-first `pull` still produces that module, which then has to stay aligned with the SQL the journal applied. The `rc` dist-tag 1.0.0-rc.5 is a pre-release and is not a candidate.
- **Kysely's `Migrator` as the plugin journal.** It runs TypeScript `up` / `down` functions from one folder, in alphanumeric filename order, with an optional `allowUnorderedMigrations`, and it holds a connection. Plugin packages arrive as installed artifacts, their dependency edges are manifest ports, and their migrations are SQL under a role that can `CREATE` in one schema. A TypeScript migrator inside the plugin process would also give that process a database connection, which ADR-0001 forbids. Admission parses SQL.
- **Prisma ORM 6** (`@prisma/client` dist-tag `prev` is 6.19.3). The register rejects it for this project because of generated-type compile cost and codegen coordination. Spike A did not remeasure it. Security patches for 6 continue until 19 November 2026 ([release status](https://www.prisma.io/docs/orm/release-status)). The fallback on an ergonomics failure is Drizzle, never Prisma (plan §3.0).
- **Prisma ORM 7.10.1 with `@prisma/adapter-pg`.** Driver adapters are required. The adapter sits on `pg`, so a pinning or pooling failure of `pg` is a failure of this stack too, and the register's rule is to redesign the tenancy substrate rather than swap ORMs. Spec §18's "pinning unproven" objection is now an objection to this unmeasured adapter. `prisma generate` is still required, and the schema file is still the source. The generated client is still a project-wide artifact.
- **Prisma ORM 8** (`prisma` 8.0.0-rc.27, `@prisma/orm-postgres` 8.0.0-rc.20). Release candidate. The release-status page, with a table dated 23 October 2026, expects general availability in October 2026 and lists transaction isolation levels among the APIs that are not available yet. The 8.x CLI does not read `schema.prisma`. [Supported versions](https://www.prisma.io/docs/orm/supported-versions) give PostgreSQL a minimum of 15 and a driver built into `@prisma/orm-postgres`, which is a different substrate from `pg` and was not measured. A query on `db` inside the transaction callback runs on its own connection, which is the wrong shape for a single `set_config` scope. `@prisma/client` stays at 7.10.1 and is not the ORM 8 library.
- **Raw `pg` as the kernel client.** The A1 control shows it pins a transaction when the caller holds one client. It does not give a derived row type, so a schema drift is not a compile error. D06 exists for that fail-closed property. Raw `pg` stays the diagnostic control in the suite.
- **Schema-per-tenant, dedicated databases in v1, and a generated client that unions every plugin.** D05 and spec §18 already reject the first two. A union client puts plugin nouns in the kernel and changes the kernel whenever a plugin ships a table.
- **Session `SET`, or relying on `DISCARD ALL` between transactions.** Transaction pooling does not run the reset query. `set_config` with `is_local` false applies for the rest of the session. The spike measured the state that survives. ADR-0007 is the recovery.

## Flip conditions

These match D06 and plan §3.0. The spike's pass means none of them is open.

- **Driver-level failure** of connection pinning, of transaction-local `set_config`, or of PgBouncer transaction mode, established by the plan §3.0 protocol (the raw-`pg` control fails the same way, effective config recorded, at least three runs): redesign the tenancy substrate. Do not swap in Prisma. Drizzle on `pg` is the same substrate and is not a remedy for that class.
- **Typecheck failure at the A5 acceptance point** (band 75, 375 queries, above 120000 ms or 3906250 KiB on the CI runner class, TypeScript 5.9.3, corpus lint intact): fall back to Drizzle and rerun A1–A5 on that client before any schema work. Do not fall back to Prisma. An overrun at band 200 or 400 is a budget input and does not choose an ORM. The measured curve did not overrun.
- **Unnamed-statement discipline itself fails** (a non-empty name on the default client): that is driver-level, per the plan. The overhead result does not flip the client. A4b remains available and unadopted.
- **A future pooler no longer replays `search_path`.** ADR-0007's flip applies. Re-measure before removing the socket discard. The ORM choice stays.
- **Adopting Kysely 0.29.7, the 0.30.0-beta.2 `next` tag, TypeScript 7.0.2, or Prisma ORM 8.** Each one is a new measurement on the rows it can affect, written down as its own note. None of them is authorized by the registry having moved.
- An invalid environment produces no verdict and no flip. The packet-filter run in the spike report is that case.
